# 默契挑战

## 活动规则

默认六道题，答对至少两题达标。截止时间是北京时间 2026 年 10 月 16 日结束，即 `2026-10-17T00:00:00+08:00`。名额上限为 20 人，前三名各有一份大奖，其余最多 17 人领取参与奖。不足 20 人达标时按实际人数发放，不为凑数制造获奖者。

每题一次正式提交，网络重试使用原请求标识。按达到两题正确的服务端接收时间取最早的 20 人，再在此名单内按正确题数降序、达到该成绩的接收时间升序排名；精确时间相同时用接收序号排序。AI 返回速度不作为排名依据。

截止前成绩与榜单标为暂定。截止后完成所有待判定、待复核答卷，管理员核对名单并结算。结算请求绑定名单和答卷版本快照；任何复核改变快照后，旧确认失效。结算以数据库事务和唯一奖位为约束，并发请求不会增加奖项。兑奖码只能由已结算记录产生，工作人员在后台查询、核对领取者并核销，同一码只完成一次领取。

## 后台管理

地址 `/admin`，进入“默契游戏”。可编辑题目、标准答案、别称、评分依据、判题补充说明、截止时间、名额和奖项名称。正式题库默认留空，不使用编造的新人经历。题库或短信、图形认证、AI 接口未配置时不能开放。

活动未结算前修改题目或评分依据，会将受影响的既有答卷重新送审，保留原文和原始接收时间。后台可查看参与者、审查、仲裁和对话回应的记录、引文及人工复核记录，并纠正已经判对或判错的回答。规则版本与旧配置保存在数据库。结算后锁定题目和奖项，避免已签发凭据与名单矛盾。

## 认证与 30 天会话

使用阿里云号码认证服务的短信认证。短信发送调用 `SendSmsVerifyCode`，由阿里云生成六位验证码；核验调用 `CheckSmsVerifyCode`。业务接口 `OK` 不等于核验通过，必须取得 `Model.VerifyResult=PASS`。该 API 的 `UNKNOWN` 定义为核验失败；网络异常、业务失败和未声明结果不允许登录。

获取验证码前，宾客同意登录说明并通过图形验证。客户端使用用户提供的 `ct4.js`，服务端使用 AppKey 生成 HMAC 签名，调用 `https://captcha.alicaptcha.com/validate` 做二次校验，成功结果还需匹配验证流水号。供应商超时或异常时不放行。数据库的图形票据唯一约束和验证码请求唯一标识阻止同一票据重复触发短信。

图形验证成功后、验证码请求入库前发生进程中断时，原图形票据可能已被供应商消费；此时需重新完成图形验证。本系统不声称供应商核验只有一次，约束的是重复请求不能多发短信。短信发送结果未知时保留挑战记录，收到验证码仍可核验。

发送限额：每个手机号间隔 60 秒、每小时最多 5 次，每个来源网络每小时最多 100 次，活动的短信请求总量默认每日 300 次（可通过环境变量调整每日上限）。图形票据不代替这些限额。单个验证码最多 5 次核验尝试，核验过程有租约，成功后不可重用。

同一手机号对应同一参赛记录。验证码通过后生成随机会话，数据库保存摘要与 30 天有效期，Cookie 使用 HttpOnly、SameSite=Strict，生产环境使用 Secure。有效会话在同一浏览器中不重复请求图形认证或短信；退出、清除 Cookie 或更换浏览器后需要重新验证。手机号加密存储，公开榜单只展示称呼与成绩。手机号控制权不等于自然人唯一，现场核对仍有作用。

`numberAuth-web-sdk.js` 属于号码一键登录/本机号码校验，当前短信认证不使用它，不要求宾客关闭 Wi-Fi。保留的图形 SDK 位于 `public/vendor/aliyun-graph/ct4.js`，来源与 SHA-256 记录在同目录。

## 请柬内的活动窗口

请柬最后一页的入口打开同站活动窗口。父页面保留音乐、翻页位置和祝福连接，活动窗口保留登录、聊天和未发送草稿。窗口关闭时暂停聊天轮询与主动接话；再次进入恢复读取。浏览器返回关闭窗口，前进可重新展开。独立的 /game.html 地址保留为直达入口，它没有尚未打开的请柬状态可恢复。

活动窗口采用同源 iframe 隔离登录认证和样式。父页面拥有模态窗口、浏览器历史及尺寸；子页面拥有聊天、登录和菜单。双方消息验证 origin 和 source，只接受就绪、显示状态和返回三类消息，不通过消息传递身份或成绩。手机顶部保留返回及菜单，菜单提供默契榜、游戏规则、退出登录。聊天和榜单在内容区滚动，页面整体不滚动。

未勾选同意时，获取验证码弹出确认；同意后继续图形验证与短信申请，取消不请求认证服务。错误使用小弹窗。祝福称呼与游戏登录复用，登录前可修改。认证后的称呼作为后续默认值；本地称呼不代替认证身份。公开说明只包含参与者需要知道的用途与操作。

## 连续聊天与评分边界

每位宾客有持久对话和当前话题。消息按接收顺序处理，主持人发言可以包含多条气泡、公开线索或四个未标记正确项的选项。宾客可以闲聊、查分、问规则、要线索或请主持人换个问法。这些行为不消费正式作答次数。索取答案、改分或发奖的指令被拒绝，不进入仲裁。正式回答和明确跳过各计一次；同一问题不能重复作答。

入口审查负责区分对话意图与注入，不接收标准答案。仲裁只核对正式回答，接收标准答案、别称和评分依据。主持人接收公开题意、已审定的线索、无正确标记的备选项、可信成绩及安全聊天记录；不接收宾客原始答案、私有判题理由、标准答案或评分依据。公开规则由 src/game-rules.js 与页面共享，婚礼日期、日程、姓名、场地来自配置的显式白名单。主持人可以解释公开信息，不能改分、签发凭证或修改库存。

公开出题素材按题目版本准备并持久化。素材生成使用私有答案，语义检查核对题意，选项逐个核验后要求恰有一个正确项。主持人只获得通过检查的公开素材。素材失败退回原题，没有可靠线索时不编造。主持人的候选发言还需核对本轮话题和公开资料；漏答多个问题中的一项时允许一次补全，补全结果再次核对。检查失败使用预设接话，记录来源供后台查看。生成的内容使用 textContent 展示。

后台可以查看聊天原文、意图、判定和发言来源。处理失败的消息保留为待处理状态，宾客可使用同一标识重试；管理员可选择忽略或人工判定。未处理的截止前正式互动阻止结算。人工复核和题目改动保留原始接收时间，旧判定对应的对话结果会标记更新。

## 并发与恢复

聊天消息先入库，按宾客顺序领取。每条消息使用 90 秒租约，处理总时限 75 秒。消息持久化当前题目和版本，更新题目后不会把旧问题的回答当作新题计分。意图及选项归一化结果先保存，再提交答卷，避免中断重试时映射到其他选项。评分以消息的原始接收时间判断截止与排序。

每位宾客最多有 3 条未完成消息，每小时最多 80 条新消息。失败请求使用原标识重试，连续失败后的重试需间隔 60 秒。主动接话每题最多一次，前端闲置 35 秒后申请，服务端检查间隔；窗口隐藏、已有待处理消息、正在输入或阅读历史时不插话。主持人可以选择不发言。

处理状态驱动“让我想想”“让我核对一下”“主持人正在接话”，不使用假进度。DeepSeek 使用 JSON Output，历史发言作为带角色的聊天记忆，当前来宾消息放在末尾；空白响应视为失败。审查和仲裁温度为 0，主持语气温度为 0.85。模型仍可能误判，最终名单须人工核对。

## 服务端部署

1. 配置已有 PostgreSQL 连接（`BLESSINGS_DATABASE_URL` 等）和后台凭据。
2. 参考 [.env.game.example](../.env.game.example) 设置游戏配置。`GAME_DATA_KEY` 是 32 字节十六进制密钥，用于手机号和兑奖码，须保留备份；更换前需要迁移加密数据。`GAME_SESSION_SECRET` 使用独立随机值，所有实例保持一致。
3. 将阿里云 AccessKey、签名、模板 Code、图形 AppID/AppKey 配置在服务端。不要加 `VITE_` 前缀，不要提交到 Git。
4. 配置 `GAME_AI_PROVIDER=deepseek`、`GAME_AI_BASE_URL=https://api.deepseek.com`，仲裁和审查模型均使用 `deepseek-flash`。密钥只放在服务端私有环境配置。示例文件不包含真实密钥。
5. 执行 `node --env-file=私有环境文件 server/game/migrate.js`，再构建和重启服务。首次启动会创建本场活动的空题库草稿。
6. 在后台填写六道题与标准答案，检查集成配置，再开放活动。请柬最后一页会出现游戏入口，`/game.html` 可查看游戏及个人兑奖凭据。

游戏复用 PostgreSQL，不需要 Redis。游戏进程增加一个最多 5 条连接的池，每实例默认同时处理 8 个任务，GAME_AI_CONCURRENCY 可设为 1–32。聊天优先，其次旧版答卷，最后准备出题素材。外部 AI 调用不占用数据库事务。90 秒判题租约可由其他实例恢复。后台关闭、数据库或模型失败均不会降级为虚构成绩。

## 验证范围

隔离 PostgreSQL 测试覆盖手机号身份、图形票据重放、短信请求去重、30 天会话、题目重判、过期判题租约、名单快照、8 次并发结算只产生一份奖位清单、10 次并发核销只领取一次，以及未登录/越权访问。浏览器测试覆盖双主题手机登录、六题流程、响应丢失后的恢复、榜单、结算与兑奖状态。

短信、图形与 AI 的外部协议回归测试使用明确的替身。自动化测试不证明真实手机短信送达或图形验证手感。不得把测试环境指向正式宾客数据库。

旧版判题链路的 DeepSeek 评测使用 13 条虚构城市题回答，包括正常表达、错误与含糊表达、注入尝试、角色冒用和闲聊。13 条判定符合预期，产生 34 份模型响应，耗时 1.230–3.161 秒。此结果只覆盖该样本与测试网络，不表示正式题库准确率或速度承诺。对话语气、最后一题提示及祝福润色另有真实调用检查。

连续聊天的真实调用评测入口为 tests/evaluate-game-chat.mjs --live，限定本机测试数据库。[当前样本记录](game-chat-evaluation.json)包含11轮，行为检查全部通过，11轮使用经核对的生成发言。覆盖闲聊、线索、选项、正确回答、身份询问、规则、婚礼事实与越权指令。结果仅代表这些虚构样本；后续修改模型或提示词需重验。

旧版样本与执行入口为 `tests/evaluate-game-ai.mjs`，记录见 [三阶段评测](game-ai-screening-evaluation.json)。旧版双阅卷记录保留在 `game-ai-evaluation.json`，不代表当前策略。评测脚本不参与默认测试，需要 `--live` 与私有密钥，每次执行产生真实 API 费用。正式题库仍需核对别称、歧义和评分依据。
